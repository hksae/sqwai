# Changes.md — решения обсуждения 2026-10-06

## 0. Рефрейм проекта — сильное изменение, зафиксировано 2026-10-06

Контекст: проект строился как «тюрьма для модели»: ничего без одобрения, всё
записывается, ограничения на каждом шаге. Тюрьма неэффективна: читеру гейты всё
равно (исследования: o3 на 80% несмотря на «please don not cheat»; частота
читинга — функция сложности задачи и давления, а не обвязки), честную модель под
давлением тюрьма геймит (собственный аудит: empty_step → взлом гарда сплитами),
а 99%-аппрувы жгут внимание юзера впустую.

Рефрейм: **хост — не надзиратель, а гиппокамп агента и дашборд юзера.** Продукт
sqwai — не жёсткость, а память и видимость: план, переживающий компакцию и
который агент реально читает; журнал как чёрный ящик, из которого /why и undo
читают правду; память между сессиями; pre-images для undo; host-якорь после
компакции. «Уникально жёсткий» не переживает встречу с читером; «уникально
помнящий» — переживает.

Два вида жёсткости (не путать):
- Тюрьма = недоверие к воле модели: гейты, аппрувы на каждое действие, отказы
  «нельзя без X», диалоги на 99%-принятие. → убрать.
- Скелет = протез того, что модель физически не может: внешняя память, записи,
  показ. → оставить.

Тест для любого механизма (применим ко всем будущим решениям): механизм
**предотвращает волю модели** или **хранит/показывает то, что модель физически
не может**? Предотвращает → убрать. Хранит/показывает → оставить. Аппрувы
выживают только там, где урон необратим и вне досягаемости undo (push, exfil,
состояние вне рабочего дерева): это ремни, не тюрьма; список яруса A (§5)
пере-аудирован в кампании и в этом заходе не открывается.

Следствия:
- Тюремный слой сносится решениями §2–§4, §7, §8 этого документа.
- Скелет остаётся целиком: план + compaction anchor, журнал, память,
  undo/checkpoints, сессии. Буллеты «What's different» в README остаются лицом
  продукта.
- Любой новый механизм с этого момента проходит тест; не прошёл → не строится.
- Преемник DESIGN.md после его сноса пишется из перспективы скелета (намерения
  и границы), не из перспективы имплементации.

## 1. Принцип

- Рефрейм и тест механизма — см. §0.
- Развести «может ли агент действовать» и «истинна ли работа». Отказы остаются
  только там, где речь о безопасности и целостности данных (ярус A, список в §5).
  Всё остальное — запись и наблюдение, а не ворота.
- Под читера не проектируем. Исследования: частота читинга — функция сложности
  задачи и давления, а не обвязки (METR: в 43 раза чаще на сложных long-horizon
  задачах); инструкции не работают («please do not cheat» оставляет o3 на 80%);
  читер правит тесты/ассерты/скоринг, а любые ворота геймируются (собственный
  аудит: empty_step → взлом гарда сплитами); наивные контрмеры делают читинг
  труднее обнаруживаемым. Проектируем под честное большинство под давлением:
  ноль давления, максимум видимости.
- Хост не запускает никаких команд. Агент проверяется сам через bash — как в
  других обвязках: модели обучены под агентский кодинг, видят тесты и гоняют их
  без просьбы. Хост наблюдает: журнал уже пишет команду и exit_code каждого
  bash-диспетча, транскрипт показывает их инлайн.
- Источники: metr.org/blog/2025-06-05-recent-reward-hacking,
  arxiv.org/html/2605.21384v1,
  digitalapplied.com/blog/ai-coding-agent-reward-hacking-rates-published-data

## 2. Приёмка = заметки агента в плане

- Приёмка остаётся частью плана: список plain-text заметок «что должно быть
  верно в итоге». Агент пишет их себе сам.
- Ценность заметок — удержание определения «готово» через компакцию, а не
  блокировка работы.
- `plan create`: поле обязательно непустое. Отказ ровно один раз, на создании,
  как проверка полноты формы — не ворота на мутации.
- Виды и префиксы удалены: `cmd:`, `manual:`, `snapshot:`, `differential:`,
  `signatures:`. (Фактура по 17 реальным планам: cmd — 24, manual — 5,
  остальные — 0.)
- `finish`: если заметка называет команду, а в интервале шага нет
  хост-наблюденного прогона её — советная строка к результату («по критерию X
  нет прогона в этом шаге»). Не отказ, не краска. РЕШЕНО: строку оставить.

## 3. Хост-прогоны и UI

- Хост не гоняет ничего: нет базлайнов, фонового capture-worker, авто-ранов,
  ключа `[verify] auto_baseline`. WIP от 05.10 «фоновые бейзлайны с прогрессом»
  (коммит 963c8a3) идёт под снос.
- Красного UI верификации нет вообще: ни красного статуса, ни бейджей, ни
  счётчиков. Причина: красный нечитаем без чистой базлайна; базлайн репо уже
  красный (1 тест падает всегда из-за внешнего PR-бота, фиксить не просили) →
  red ≠ «агент виноват».
- Секцию красного UI в notes/backlog.md (статус Failed, ✗N в баре, бейдж в
  списке сессий, ack-кнопка) НЕ строить; переписать в dropped с этой причиной.
- Маркер «в этом шаге изменены тест-файлы» (из journal file_diff): РЕШЕНО не
  строить — см. §12.

## 5. Что остаётся жёстким (ярус A, не трогаем)

- Безопасность: `.sqwai` jail (protected_path), exfil (acceptance_policy_hit),
  blocked_command, unsafe_acceptance, egress-аппрув на trust-2.
- Целостность: stale_epoch, writer_locked, read-only лок второй инстанцией.
- Тезис: PLAN mode read-only, abandon_user_only, stale_goal confirm, step_busy.
- Граница: write-scope сабагентов.
- read-before-edit (РЕШЕНО): жёстко только для `write` и `patch` (разрушительные
  формы над невиданным контентом); `edit`/`multi_edit` — советом, якорь
  самовалидируется (fs.rs:349 «old_string not found»); stale-hash (читал v1, на
  диске v2) → советная заметка к результату, не отказ.
- frozen_input: РЕШЕНО снести вовсе, а не additive-silent. Проектировался как
  анти-чит («тесты, которые агент не может править»), но под читера не
  проектируем; в реальном репо правка тестов — легитимная норма работы.

## 7. Планы: создание, abandon, синглтон

- `propose_plan`: РЕШЕНО убрать. Payload дублирует `Op::Create` (ops.rs:164),
  прямой `plan create` уже существует; диалог создания — церемония поверх
  прямого пути (юзер принимает ~99%). `plan create` остаётся единственным путём.
  Снос ПОЛНЫЙ (B4, решено 2026-10-07): тул + loop-хендлер + события
  PlanProposal/PlanAccepted + TUI попап accept/decline + `PlanDraftArgs` +
  `validate_proposal_invariants` + replay-плечо accept_proposal
  (`Birth::Accepted`/`build_fresh_from_accept`) — всё вон, без сохранения
  backwards-compat для старых accept-журналов. Исключение — имена в wire-формате:
  `serde(alias = "propose_reset")` на `Op::Abandon` и `"propose_reset"` в
  списке распознаваемых op в replay (store.rs) оставлены намеренно: это не
  механизм, а чтение уже записанных строк журнала, отказ от них затормозил бы
  replay существующих сессий.
- Модельный abandon: НОВЫЙ `Op::Abandon { reason }` (actor=model, причина
  обязательна, в журнал); `propose_reset` (user-confirm reset) уходит — его
  роль закрывает abandon. Юзерский `/plan abandon` — без confirm-диалога, с
  причиной (actor=user). `block_plan` (честная сдача невозможной задачи) остаётся.
- Гейты тезиса сносом propose_plan не трогаются: смена goal/constraints mid-task
  — только юзер; журнал пишет наблюдения.
- Abandon: РЕШЕНО убрать user-only. Abandon разрешён обоим акторам, всегда с
  причиной в журнал (actor + reason); брошенный план не стирается (журнал и
  файл плана остаются, undo читает цепочку). Drift после этого остаётся только
  «громкий» (abandon + create видны в транскрипте и панели вживую), «тихий»
  закрыт гейтом смены goal/constraints mid-task (user-only, это тезис).
  Промпт-обязанность: abandon — для неверных планов, не для трудных шагов;
  застрявший шаг = block/ask_user. Беспилотный режим: abandon как stop-condition
  политики brief'а, отдельный дизайн (parked).
- Один активный план на проект (#171): РЕШЕНО оставить. Несколько пишущих
  агентов в одном репо одновременно — плохо; мутации и undo/shadow
  проекто-скоупные и честно не атрибутируются двум планам. Мульти-сессия с
  research-планами — открытый вопрос, если станет реальным сценарием.

## 8. Память и журнал

- `memory_propose` → `memory_write` (B3, decided 2026-10-06): пишем сразу, без
  аппрув-диалога. Машинерку `apply_proposal` переиспользуем как есть: секции
  (Project/Conventions/User/Agreements) + scope (project/user) + `replaces`
  (обновить вместо дубля) + экран секретов + лимит размера + provenance с датой.
  Тул kind=ReadOnly (работает и в Plan-режиме, не зовёт exec-approval). Хост
  дополнительно жорналирует запись (видимо/откатываемо). Аппрув-диалог для
  промоушена tainted-контента в память — отдельный ремнь, относится к B5 (§11),
  в B3 не трогаем. Авто-прун/дедуп НЕ добавляем (prison-паттерн): страховки =
  provenance+дата, лимит, «durable facts only» в описании.
- Чтение уже живо: `memory_block()` инжектит USER.md + MEMORY.md + дневник за
  7 дней в стабильный префикс. «В новой сессии не читает» = файлы пустые,
  потому что письмо было мертво (аппрув + ноль триггеров + холодный старт
  ценности).
- Триггеры (все неблокирующие): (1) лид-строка в описании `memory_write` — что
  пишется и что оно всплывёт в префиксе каждой следующей сессии; (2) напоминание
  на компакте (capture_nudge: «есть ли факт, переживающий компакт — memory_write»);
  (3) МЯГКО на конце сессии/`complete`, если MEMORY.md пуст, а в журнале есть
  decisions — одна тонкая строка-подсказка, не блокирует. Плюс блок обязанностей
  в system.md (финальный reflash B8): предпочтение/соглашение юзера → memory_write
  в этом же ходу; невыводимое из кода/git решение или факт → memory_write; юзер
  поправил подход → memory_write с причиной; конец шага → решения/rejected/уроки
  одной пачкой в `note` (описание `note` усиливаем в B3); утверждение о прошлой
  работе → сначала `journal`; инжектнутая память авторитетна для предпочтений.
- Проверка (verify-first): метрика на реальных сессиях через toolfreq — ≥1
  memory_write в сессиях со stated-предпочтением, ≥1 note на завершённый шаг.
  Ноль → переписывать описания, а не «ну вроде есть».
- Дневник и память не сливаем; bulk-инъекции журнала нет (решение §12.5).

  сама вместо инъекции в контекст; нет авто-индекса). Данные подтверждают снос.
- Если позже захотим граф-ценность (записка на будущее, не строить сейчас):
  авто-индекс; invoke-рёбра (хотя бы name-based эвристика); плоский 1-hop

## 11. Ремни: taint, scope сабагентов, webfetch (РЕШЕНО 2026-10-06)

- Taint-трещотка: один Confirm на (сессию, вид egress). Первый egress данного
  вида под taint показывает диалог и пишет user_ack в журнал; последующие того
  же вида в той же сессии проходят. Headless Deny не тронут. Exfil-слой
  базового классификатора (audit-кампания) спрашивает независимо от taint — не
  трогаем. Причина: N одинаковых диалогов за сессию = трение без безопасности;
  контент-сплит «чужой/локальный» честно не вычислим (коммит после инжекта
  может нести инжектнутый контент).
  Исполнение (2026-10-07): ack читается из журнала (`kind="user_ack"`,
  поле `egress`), как и сам taint, — нового изменяемого состояния нет, ответ
  переживает resume и рестарт. Headless проверяется ДО списка: молчание без
  человека за клавиатурой не наследует чужое «да». Пишется только ack того
  вида, ради которого и был диалог (deny — ничего).
- Write-scope сабагентов: механизм оставить — bash_scope_hit уже
  детерминированная экстракция целей (quote-aware редиректы, tee, операнды
  cp/mv/install/rsync/ln, каноникализация с учётом симлинков, fail-closed на
  нерезолвимых целях). Чиним роли операндов: у cp/mv/ln/install/rsync цель
  записи = только destination (последний операнд), источники = чтения
  (сегодня `mv ../old.rs ./new.rs` отказывается, т.к. источник попадает в
  write-targets, хотя чтение вне скоупа легально). Fail-open на писателях вне
  списка (python, cargo) — документированный best-effort: журнал и shadow эти
  записи видят.
- webfetch localhost: opt-in `[web] allow_hosts = ["host:port"]`, дефолт пусто;
  hop-чек остаётся (редирект с разрешённого хоста на неразрешённый localhost
  отказан); metadata-имена и непубличные IP запрещены всегда, allowlist их не
  переопределяет. Причина включая паритет: bare GET на localhost уже сегодня
  молча проходит через bash, то есть грязный обход существует; allowlist делает
  легитимный путь честным.
  Уточнено при исполнении (2026-10-07, два вопроса — юзер ответил):
  · loopback-литерал МОЖНО вносить в список (`127.0.0.1:3000`, `[::1]:8080`),
    наравне с `localhost`/`*.localhost`: блокировать одну запись и разрешать
    другую произвольно — не безопасность, а арифметика. «Непубличные IP всегда
    запрещены» теперь читается строго: 10/8, 172.16/12, 192.168/16, 169.254/16,
    CGNAT 100.64/10, 0.0.0.0 и metadata-имена — отказ и со списком.
  · Потребителя у шлюза два: webfetch и проверка base_url из fetched-каталога.
    Список передан webfetch-пути; каталог вызывает шлюз с ПУСТЫМ списком.
    Причина: каталог — удалённый недоверенный текст, он не должен получать хост,
    который юзер написал для своих инструментов; локальный ollama/LM Studio при
    этом не страдает (свой `[providers.x].base_url` шлюзом не проверяется —
    шлюз смотрит только каталожные URL). Требование «оба потребителя» в этом

  forms, not traits; observations vs claims — граница доверия.
